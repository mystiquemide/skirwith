# AMD-001: Legacy payment identity and receipt compatibility after the rebrand

Status: PENDING OWNER APPROVAL (drafted 2026-08-04)
Author: Implementation lead
Approver: MystiqueMide (repository owner) - sign-off pending
Related decision: DEC-012
Related checkpoint: CP-028, CP-029, CP-030

## 1. Original persisted identity contract

Before the product rebrand, the action persisted its payment identity and
durable replay state under the `mergepay` namespace:

- Payment purpose: `mergepay:payout`.
- Payment key: `mergepay:` + SHA-256 of the stable payment identity
  (version, repository, pull request number, merge SHA, purpose).
- Receipt marker envelope: `<!-- mergepay:{...} -->`.
- Receipt marker product field: `mergepay`.
- Receipt signing secret name: `MERGE_PAY_RECEIPT_SECRET`.

Live evidence (7 confirmed transactions, 1 replay, 2 refusals) was written
under this contract in `mystiquemide/skirwith-acceptance`.

## 2. Rebrand-induced incompatibility

The rebrand renamed the persisted contract without a data migration:

- Payment purpose changed to `skirwith:payout`.
- Payment key prefix changed to `skirwith:`.
- Marker envelope and product changed to `skirwith`.
- Receipt secret name changed to `SKIRWITH_RECEIPT_SECRET`.

The same logical merge therefore derives a different payment key and request
hash. Without compatibility, a re-run of a pre-rebrand PR would compute a
`skirwith:` key, find no receipt, and could broadcast a second payment. That
violates the replay-suppression guarantee.

## 3. Dual-read behavior

The action now accepts both identities:

- New payments are written under the current `skirwith` contract
  (`skirwith:payout`, `skirwith:` keys, `skirwith` product and envelope).
- On every run the orchestrator derives both the current key and the legacy
  key, and looks up receipts under both. A receipt found under the legacy
  identity is resolved with the legacy request hash, so a confirmed legacy
  payment returns `duplicate`, a pending legacy execution resumes polling,
  and a conflicting legacy record goes to manual review. No path rebroadcasts.
- The receipt parser accepts both marker envelopes, products, and payment-key
  prefixes, and verifies both with the same receipt secrets.
- The runtime accepts `SKIRWITH_RECEIPT_SECRET` (canonical) and
  `MERGE_PAY_RECEIPT_SECRET` (legacy) for the same secret, so the live
  acceptance repository does not need to be re-secreted.

Historical live receipts are never rewritten or edited.

## 4. New-write behavior

All new receipts and markers are written in the current `skirwith` format with
the canonical secret name. Only read paths (lookup and verification) dual-read.

## 5. Migration window and removal condition

The legacy read path and legacy secret-name fallback stay in place for the
full duration of the hackathon and until the live acceptance evidence is no
longer presented. Removal condition: after the live `mergepay` receipts are
retired or the acceptance repository is closed, a follow-up AMD must record
the removal. There is no scheduled removal date.

## 6. Affected requirements and tests

- Requirements: replay suppression (`SC-002`), evidence integrity
  (`SC-004`), post-rebrand compatibility.
- Tests: `tests/evidence/receipt.test.ts` (legacy marker parse/verify),
  `tests/execution/orchestrator.test.ts` (legacy duplicate, pending resume,
  conflict, no-broadcast-on-new-payment), `tests/github/inputs.test.ts`
  (legacy secret-name fallback), `scripts/verify-packaged.mjs` (packaged
  legacy receipt produces duplicate and zero broadcasts).

## 7. Risks and rollback

- Risk: Legacy lookups add one receipt-store query only when the current key
  misses; no extra network work for new payments.
- Risk: A legacy receipt with changed content resolves to manual review, never
  to a new broadcast.
- Rollback: Revert to the `skirwith`-only contract by reverting the parser and
  key-derivation change; no live receipt is modified by either direction.
